## ۱) دو باگی که خودت گزارش کردی — علت دقیق پیدا شد

### ۱-۱. «درخواست نامعتبر» در املاک کریتور ✅ علت قطعی

`api.php` برای **تمام** درخواست‌های POST یک کلید اجباری در body می‌خواهد:

```php
// api.php:259-264
$secretApiKey = "AmLaK_Super_Secret_2026!";
if (!isset($input['api_key']) || $input['api_key'] !== $secretApiKey) {
    http_response_code(403);
    echo json_encode(['error' => 'عدم دسترسی! درخواست نامعتبر است.']);
    exit;
}
```

`index.html` این کلید را می‌فرستد (`index.html:1730` و `:1736`)، اما `amlak_creator_b_1687.php` **نمی‌فرستد**:

```js
// amlak_creator_b_1687.php:57-68 — payload فقط این فیلدها را دارد:
const payload = { id, masterPass, name, city, phone, phone2, managerName, adminPin, createdAt, expireAt };
```

تعداد occurrence رشتهٔ `api_key` در `amlak_creator_b_1687.php` = **۰**.
نتیجه: دکمهٔ «تولید کد جدید آژانس» همیشه ۴۰۳ با همان متن «عدم دسترسی! درخواست نامعتبر است.» برمی‌گرداند. این تنها جایی است که این متن تولید می‌شود (`api.php:262`)، پس تطابق ۱۰۰٪ است.

> ⚠️ نکتهٔ مهم: خود `api_key` هیچ امنیتی ندارد — چون inside `index.html` یعنی کاملاً public است. فقط یک «قفل شکسته» است که الان دارد کارکرد را می‌شکند.

### ۱-۲. «درخواست نامعتبر» موقع ثبت ملک (احتمال دوم و قوی)

همان ۴۰۳ یک مسیر دوم هم دارد: اگر حجم JSON ارسالی از `post_max_size` هاست رد شود، PHP بدنه را **کاملاً دور می‌ریزد** → `php://input` خالی → `$input = []` → `api_key` وجود ندارد → همان «درخواست نامعتبر».
و این اتفاق خیلی محتمل است چون:

- `index.html:1972` حداکثر **۱۰ مگابایت برای هر عکس** مجاز می‌داند (`MAX_MB = 10`) و تا **۳ عکس**؛
- عکس‌ها به‌صورت **base64 داخل JSON** فرستاده می‌شوند (`index.html:2030` → `images: tempImagesBase64`)، یعنی ≈۳۳٪ باد می‌کنند؛
- پس یک ثبت ملک با عکس می‌تواند بدنهٔ ۳۰–۴۰ مگابایتی بسازد، درحالی‌که `post_max_size` پیش‌فرض اکثر هاست‌های cPanel بین ۸ تا ۶۴ مگابایت است.

**پیامد مهم:** الان هیچ تفاوتی بین «کلید غلط» و «بدنهٔ دور ریخته‌شده» وجود ندارد؛ هر دو یک پیام بی‌معنی می‌دهند. باید تفکیک شوند.

### ۱-۳. پایپلاین صوت → متن

**در کل مخزن وجود خارجی ندارد.** جست‌وجوی `speech|voice|audio|whisper|transcri|mic|recorder|صوت|ویس` در `index.html` → **۰ نتیجه**. نه endpoint در `api.php`، نه input در فرم، نه ستونی در دیتابیس.
پس این مورد «باگ» نیست؛ یک **فیچر ساخته‌نشده** است و از صفر طراحی می‌شود (مرحلهٔ ۵). برای طراحی‌اش باید چند سؤال را جواب بدهی (بخش ۴).

## ۳) برنامهٔ پیشنهادی — ۶ مرحله

### مرحلهٔ ۰ — قابل‌اعتماد کردن مخزن و محیط تست (پیش‌نیاز همه‌چیز)
- باز کردن زیپ به یک درخت سورس واقعی در ریشهٔ مخزن (`public/`, `app/`, `config/`, `db/`).
- افزودن `schema.sql` کامل (بازسازی از روی کد) + `.gitignore` + `README` + حذف `uploads/*.jpg` از git.
- خارج کردن `config.php` از git → `config.example.php` + `.env`.
- ساخت یک محیط اجرای واقعی برای تست (PHP + MySQL) — **اینجا به کمک تو نیاز دارم** (بخش ۴، سؤال ۲).
- ✅ خروجی: بتوانم `api.php` واقعی را اجرا کنم و قبل/بعد هر تغییر، یک تست contract واقعی بزنم.

### مرحلهٔ ۱ — رفع دو باگ بلاک‌کننده (سریع‌ترین برد)
- A1: افزودن `api_key` به `amlak_creator_b_1687.php` + یکسان‌سازی کلید با config.
- تفکیک «کلید نامعتبر» از «بدنهٔ دور ریخته‌شده به‌خاطر `post_max_size`» با پیام خطای مشخص و راهنما.
